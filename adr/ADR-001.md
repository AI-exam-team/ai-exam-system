## 背景

`contract-v0.1.md` 2.3 已冻结：试卷 `PUBLISHED` 后，试卷结构、每题分值与时间窗口不可修改。但**题目本体**（题干、参考答案、评分点）在其被引用之后是否还允许修改、历史试卷与答卷取哪一版数据，是 C-01 留给第 8 周的问题。

具体冲突场景：

1. 教师 A 组卷并发布考试后，回头修改了原题目（改题干、改评分点分值）；
2. 学生正在作答，进入考试页时读到的是**修改后**的题干，与他此前作答时看到的题干不一致；
3. `grading` 用**修改后**的评分点评判学生按**旧评分点**作答的内容，出现评分不公；
4. 考试结束后回看历史，试卷内容已与当时不同，无法追溯。

谁在读题目：

| 消费方 | 读取时机 | 读取内容 |
| --- | --- | --- |
| exam | 发布校验、学生进入考试 | 题目 ID、顺序、分值、题干（不含评分点与参考答案） |
| grading | AI 初评 | 题干、参考答案、评分点 |

约束前提：

- MVP1 Non-Goals 明确**不做题目版本管理**（`mvp1-scope.md` 3.2）；
- MVP1 单库单实例，数据量小（题库 < 1000 题、试卷 < 50 份）；
- 跨模块只允许通过契约传递只读数据，禁止跨模块读表（`architecture.md` 4.1）。

---

## 决策

**采用「组卷时保存快照」**：教师在 `POST /api/v1/papers` 组卷时，系统在**同一事务内**把每道入选题目的 `stem`、`referenceAnswer`、`totalScore`、`type` 及全部 `rubric` 条目（`description` / `score` / `order`）深拷贝到 `paper_items` 的快照列，同时保留 `questionId` 作为追溯关联。

已发布试卷及其下游（`exam` 发布校验、学生答题页、`grading` AI 初评）**只读快照，永不回源读取 `questions` 表的最新内容**。

配套规则：

1. `PUT /api/v1/questions/{id}` 在题目被任一 `PUBLISHED` 试卷引用时返回 409（`QUESTION_ALREADY_USED` 为候选码名，待集成层在契约第 5 节登记；登记前按 409 处理）；
2. `DRAFT` 试卷不产生版本歧义（尚未发布），但其快照在组卷时即固定，教师若需换题应重新组卷；
3. 快照列一经写入不可更新（`PUBLISHED` 后）。

---

## 备选方案

### 方案 A：动态引用（`paper_items` 只存 `questionId`）

- **优点**：零冗余；题目修改自动在所有试卷生效；存储与实现最简单。
- **缺点**：
  - 考试进行中改题会导致同一场考试内学生看到的题干不一致；
  - `grading` 会用新评分点评判旧答案，破坏评分一致性；
  - 历史考试不可追溯，与「试卷发布后冻结」的契约精神冲突；
  - 一旦出现事故，是**静默的数据漂移**，排查成本极高。

### 方案 B：组卷时保存快照（✅ 采用）

- **优点**：
  - 试卷内容在组卷时即冻结，学生、教师、AI 三方看到的是同一份内容；
  - 原题修改不影响历史试卷，教师有明确的操作路径（回原题改 → 重新组卷）；
  - `exam` / `grading` 的跨模块 DTO 直接从快照组装，下游无需感知题目状态；
  - 不引入版本号概念，符合 MVP1 Non-Goals。
- **缺点**：
  - 数据冗余：一题被 N 份试卷引用则有 N 份快照；
  - 原题删除/归档后快照仍需保留（这是刻意的，已发布试卷必须保留内容）。

### 方案 C：题目版本号（`paper_items` 存 `questionId + version`）

- **优点**：冗余小于快照；天然支持「题目历史版本」。
- **缺点**：
  - 等价于提前实现「题目版本管理」，触碰 `mvp1-scope.md` 3.2 Non-Goals；
  - 所有读题目方（exam / grading / 学生端）都要理解版本语义，接口复杂度上升；
  - 需要额外的版本表与版本切换流程，第 9 周任务量不可控。

---

## 取舍与 trade-off

选 **方案 B**，理由：

1. **一致性优先于存储效率**：正式考试场景下「试卷内容冻结」是不可妥协的不变式。方案 A 的风险是静默的、影响评分公平的，MVP1 不应承担。
2. **冗余成本可忽略**：单题快照约 1~3 KB（题干 + 参考答案 + 评分点 JSON），50 份试卷 × 10 题 ≈ 1~1.5 MB，对 MySQL 8 无压力。
3. **实现集中在一处**：改动只在 qbank 组卷事务内，`exam` / `grading` 的契约与代码零改动，跨模块影响面最小。
4. **为 v2 留出空间**：若后续需要「改题后草稿试卷可同步更新」，可在快照基础上增加 `snapshotVersion` 字段演进，不改现有契约语义。

方案 C 的版本号机制属于 v2 议题，MVP1 不引入。

## 后果与影响文件

### 数据模型（qbank）

`paper_items` 在原有 `paper_id`、`question_id`、`order`、`score` 基础上新增快照列：

| 新增列 | 类型 | 说明 |
| --- | --- | --- |
| `type_snapshot` | VARCHAR | 题型快照 |
| `stem_snapshot` | MEDIUMTEXT NOT NULL | 题干快照（存储类型以 SP-04 结论为准） |
| `reference_answer_snapshot` | MEDIUMTEXT NOT NULL | 参考答案快照（contract 2.1 规定 `referenceAnswer` 必填，快照不可为空） |
| `rubric_json_snapshot` | JSON NOT NULL | 评分点数组快照：`[{rubricItemId, description, score, order}]` |
| `total_score_snapshot` | INT NOT NULL | 题目分值快照 |

约束：`UNIQUE(paper_id, question_id)`。

### 逻辑与接口

| 位置 | 变更 |
| --- | --- |
| `POST /api/v1/papers` | 同一事务内完成快照深拷贝；提交前校验 `paper_items` 行数 == `questionIds` 长度 |
| `PUT /api/v1/questions/{id}` | 若题目被任一 `PUBLISHED` 试卷引用，返回 409（候选码名 `QUESTION_ALREADY_USED`，待集成层登记） |
| `GET /api/v1/papers/{id}` | 已发布试卷按快照返回题目内容 |
| 跨模块只读读取，按 `architecture.md` 6.5 的 `PaperForExam` | 从 `paper_items` 快照组装，不从 `questions` 取；具体调用形态由集成层确定，本 ADR 不定义路径 |
| 跨模块只读读取，按 `architecture.md` 6.5 的 `QuestionForGrading` | 从快照组装；同一题在不同试卷可能是不同快照，需按 `paperId` 定位 |

### 跨模块影响

- **exam**：`PaperForExam` 契约字段不变，取值来源改为快照，对 exam 透明；发布校验逻辑无需改动。
- **grading**：`QuestionForGrading` 契约字段不变；仍需包含完整 `rubric`，且不得重算分值。
- **`architecture.md` 6.5**：需补注「qbank 侧取值来自 `paper_items` 快照」。

### 不影响

- 试卷状态机、时间窗口、交卷、AI 评分、成绩发布；
- `contract-v0.1.md` 已冻结的字段名与错误码：本 ADR **不新增错误码**，`QUESTION_ALREADY_USED` 仅作候选码名，待集成层在契约第 5 节登记后生效。
