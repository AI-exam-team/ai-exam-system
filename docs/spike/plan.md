## 2. SP-01 DeepSeek 结构化评分输出、延迟与费用

**验证问题**

> 给定题干、参考答案、评分点与学生答案，DeepSeek（OpenAI 兼容接口）返回的 JSON 有多少比例能通过契约要求的完整结构校验？P95 延迟与单次费用是多少？

**假设**

- 通过系统提示词 + 明确的 JSON 输出约束，20 次调用中至少 18 次能直接通过结构校验（评分点 ID 完整、无重复、分数与 `hit` 一致、合计等于 `aiScore`）。
- P95 延迟不超过 30 秒，单次调用费用可估算且在课程预算内。
- 超时或非法输出可以稳定地触发 `FAILED`，不需要人工干预数据。

**实验步骤**

1. 构造 3 个样本：10 分简答题（2 个评分点）、20 分论述题（4 个评分点）、学生答案为空字符串。
2. 使用与生产相同的提示词模板，每个样本调用 7 次（共 21 次，取 20 次有效），记录：请求时间、响应时间、HTTP 状态、token 用量、费用、原始响应。
3. 用独立脚本执行契约第 3 条（ADR-003「输出校验」）的校验逻辑，统计通过率与失败类型。
4. 模拟 1 次超时（降低客户端超时阈值）与 1 次非 JSON 响应，确认失败路径可识别。
5. 密钥只用环境变量 `DEEPSEEK_API_KEY`；样本不得包含真实学生数据。

**成功标准（建议值，评审时确认）**

- 结构校验通过率 ≥ 90%（20 次中 ≥ 18 次）。
- P95 延迟 ≤ 30 秒；超时率 ≤ 5%。
- 能给出单次平均 token 与费用估算。
- 若未达标：在 ADR-003 中修订为异步 202 + 轮询，或调整提示词与输出约束后重测。

**产出**

- `README.md`：结论先行（可行 / 不可行 / 有条件可行）+ 数据表 + 原始响应样例（脱敏）。
- `evidence/`：脱敏的日志与耗时、费用截图。
- `prompt.md`：提示词版本（与 AR-6.7 的 `promptVersion` 对应）。

**明确不做**：不实现 `AIService`、不写评分业务逻辑、不接数据库、不合并 `src/`。

## 3. SP-02 MySQL 并发交卷幂等

**验证问题**

> 在 MySQL 8 下，用「唯一约束 + 条件更新」能否保证手动交卷与重复请求并发时只发生一次状态迁移？

**假设**

- `(paperId, studentId)` 唯一约束 + `UPDATE ... WHERE status = 'DRAFT'` 的条件更新，在 50 个并发重复请求下只产生 1 次成功，其余返回冲突。
- 已交卷内容、`submittedAt` 不被后续请求覆盖。

**实验步骤**

1. 建最小表：`answer_sheets(id, paper_id, student_id, status, submitted_at, version)`，加唯一约束。
2. 用 50 个线程同时提交同一份答卷的交卷请求；分别测试纯唯一约束、条件更新、两者组合。
3. 记录成功数、冲突数、最终 `submitted_at`、行数；重复 10 轮。
4. 模拟「手动交卷 + 到点自动交卷」同时到达，确认只迁移一次。

**成功标准**

- 每轮恰好 1 次成功状态迁移，其余请求被拒绝，数据库只有 1 行、`submitted_at` 不被改写。
- 结论能直接落到 ADR-002 的具体 SQL 与错误码（409 `EXAM_ALREADY_SUBMITTED`）。

**产出**：`README.md`（含建表语句、并发脚本说明、10 轮结果表）、`evidence/`。

**明确不做**：不写答题页面、不接 Spring 业务层、不合并 `src/`。

## 4. SP-03 自动交卷触发方式与调度漂移

**验证问题**

> 在单实例 Spring Boot 下，定时扫描（`@Scheduled`）与「学生下次请求时惰性触发」两种方式，哪一种能在 `endAt` 后可靠地把 `DRAFT` 答卷置为 `SUBMITTED`，且不会重复交卷？

**假设**

- 单实例定时扫描每 30 秒执行一次，在 `endAt` 后 60 秒内可完成全部到期答卷的自动交卷。
- 定时扫描与手动交卷并发时，条件更新保证只有一次迁移（复用 SP-02 结论）。
- 惰性触发实现更简单，但存在「无人访问则永不交卷」的漏洞，不能单独使用。

**实验步骤**

1. 用最小 Spring Boot 工程（独立于本仓库 `src/`，放在探针目录）建立 10 份 `DRAFT` 答卷，`endAt` 设为当前时间后 1 分钟。
2. 分别运行：A 仅定时扫描；B 仅惰性触发；C 定时扫描 + 惰性兜底。
3. 记录每份答卷的 `submittedAt` 与 `endAt` 的差值、重复迁移次数、进程重启后的行为。
4. 记录单实例假设下的调度漂移与补偿策略。

**成功标准**

- 方案 A 或 C 在 `endAt + 60s` 内完成 10/10 自动交卷，0 次重复迁移。
- 结论明确写入 ADR-002：采用哪种触发方式、扫描间隔、重启后的补偿规则。

**产出**：`README.md`（三种方案对比 + 时间线）、`evidence/`。

**明确不做**：不引入 Quartz、调度框架或消息队列；不合并 `src/`。

## 5. SP-04 长文本答案与 utf8mb4 存储

**验证问题**

> MySQL 8 + utf8mb4 下，单题 20KB / 50KB 中文答案、含 emoji 与换行的文本能否完整往返？字段类型选 `TEXT` 还是 `MEDIUMTEXT`？

**假设**

- utf8mb4 下 20KB 中文答案可完整存取；50KB 需要 `MEDIUMTEXT` 或明确限制输入长度。
- 换行、引号、emoji、特殊符号不发生截断或乱码。

**实验步骤**

1. 建最小表，分别用 `TEXT` 与 `MEDIUMTEXT` 存储 20KB、50KB 中文样本（含 emoji、换行、引号）。
2. 写入后读回，逐字节比较长度与内容摘要；记录报错或截断。
3. 在接口层建议输入上限（与前端字数限制一致）。

**成功标准**

- 给出明确的字段类型与输入上限建议，能直接用于 qbank 题目与 exam 答案表设计。
- 20KB 样本 100% 往返一致；50KB 若有问题，给出可行替代（`MEDIUMTEXT` 或限制）。

**产出**：`README.md`（字段类型建议 + 复现 SQL）、`evidence/`。

**明确不做**：不做全文检索、不引入 Elasticsearch。

## 6. 结论回流与评审

1. 每个探针完成后，在目录内 `README.md` **结论先行**，写 `结论：可行 / 不可行 / 有条件可行`。
2. 涉及契约或架构的结论，当天更新 ADR 或 `docs/architecture.md`，不让结论只留在探针目录。
3. 探针由集成负责人评审；涉及模块实现方案的，请对应模块 owner 确认。
4. 探针代码不合并到 `main`；如确需保留，只保留在 `docs/spike/spike-<topic>/`。
5. 时间盒到期仍未完成：停止实验，输出阶段性结论与阻塞原因，不无限延期。
