## 四、跨模块接口变更流程

任何影响两个及以上模块的变更（字段、事件、API、数据库结构、状态机）按以下顺序：

1. **先改契约**：在 `spec/`（契约章节）或 `adr/` 提交变更 PR，说明动机、影响面、兼容策略与回滚。
   - 分支：`docs/issue-<编号>-<简述>`
   - 评审：集成负责人 + 所有受影响模块组各 1 人。
2. **契约合并后再实现**：各模块组基于更新后的契约拉分支实现，禁止“代码先行、契约后补”。
3. **集成验证**：集成负责人组织端到端联调，验证通过后各 PR 才能合并；验证证据写入 PR 的“测试证据”栏。
4. **变更留痕**：契约变更在 ADR 中登记编号，相关 Issue 与 PR 互相引用。

紧急修复也遵循同一顺序；允许先合修复、当天补契约，但必须在 Issue 中记录例外原因。

## 五、每周合并节奏

| 时间 | 动作 | 说明 |
| --- | --- | --- |
| 周一 | 周会排期 | 把 Backlog 中确认的任务移入 This Week，指定 Owner |
| 周二～周四 | 日常开发 | 小 PR、早评审；模块组内互评 |
| 周四 18:00 | 首次合并窗口 | 完成本周主功能合并 |
| 周五 12:00 | 第二次合并窗口 | 只收修复与文档，不再开新功能 |
| 周五下午 | 集成验证 + 看板核对 | 集成负责人跑端到端；看板全部卡片归位 |
| 演示/提交前 24h | 冻结 | 只允许 P0 修复，需集成负责人同意 |

- 一个 PR 建议不超过 400 行有效变更；超过则拆分或先写 ADR。
- 合并方式建议 **Squash merge**，保持 `main` 线性；合并后删除任务分支。
- 每日站会只看板，不逐人汇报；卡片不动的 Owner 需说明阻塞。

## 六、冲突处理

1. **文本冲突**：作者先 `rebase` 到最新 `main` 解决，禁止用 `--force` 覆盖他人提交；解决后重新请求评审。
2. **契约冲突**：两份 spec/接口定义不一致时，暂停相关 PR，由集成负责人召集受影响组，按第四节流程出一版契约；有分歧时以 ADR 记录取舍。
3. **代码归属冲突**：同一文件被多组修改时，由该路径 CODEOWNERS 决策；跨路径的由集成负责人裁决。
4. **评审僵持**：模块组内 2 人意见不一致时，升级到集成负责人；仍不一致则在周会决议并记入 ADR。
5. **回滚优先**：已合并变更导致 `main` 不可用时，先回滚（`git revert`），再排查，不在 `main` 上直接修补。

## 七、角色职责速查

- **模块 Owner（每组 2 人）**：认领本模块 Issue、保证 spec 与实现一致、评审组内 PR、维护本模块测试。
- **集成与契约负责人（李昕彤，兼任）**：维护 `spec/spec-v*.md` 与 `adr/`、把关跨模块变更、组织集成验证、看板与周节奏。
- **评审人**：至少 1 名非作者；涉及契约时必须有集成负责人。
- **全员**：Issue 先行、PR 绑定 Issue、只从 `main` 拉分支、不直推 `main`。
