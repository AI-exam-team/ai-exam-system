# 技术探针（Spike）规范

本目录用于记录技术预研（spike）活动。技术探针的目标是**在投入正式实现前降低不确定性**，不是交付业务功能。

> 第 6 周仓库不包含业务代码；本规范先行，第 7 周起按此执行。

## 一、什么情况需要开探针

- 技术方案存在多个可行路径，需要实测对比。
- 关键第三方依赖或外部接口（如 DeepSeek OpenAI 兼容接口）的行为、限流、费用不确定。
- 性能、兼容性、部署方式存在明显风险。
- 需求方与团队对可行性判断不一致。

## 二、允许的探针类型

只允许以下五类，超出范围需先在 `adr/` 说明理由：

| 类型 | 典型问题 | 示例 |
| --- | --- | --- |
| 外部接口验证 | 接口是否兼容、认证方式、限流与错误码 | DeepSeek OpenAI 兼容接口的鉴权、超时、重试行为 |
| 数据与模型验证 | 表结构、字段长度、字符集、事务边界 | 主观题答案长文本存储、评分点结构 |
| 框架/版本兼容 | 依赖版本组合是否可构建、可部署 | Java 21 + Spring Boot、Vue 3 构建链 |
| 性能与容量 | 响应时间、并发上限、成本估算 | 单次阅卷调用耗时与 token 费用 |
| 部署与运维 | 本地/Docker 可复现性、配置注入 | 后端 + MySQL 的 Docker Compose 启动 |

禁止把探针当作“提前写功能”的借口；产品功能、UI 页面、正式业务逻辑不属于探针。

## 三、命名与目录

- 一个探针一个目录：`docs/spike/spike-<topic>/`，其中 `<topic>` 使用小写英文与连字符，例如：
  - `docs/spike/spike-deepseek-api/`
  - `docs/spike/spike-mysql-rubric-schema/`
  - `docs/spike/spike-docker-compose/`
- 分支命名：`spike/<topic>`，从 `main` 拉出；**探针分支不合并到 `main`**，结论通过文档 PR 回流。
- 每个探针目录至少包含：

```text
docs/spike/spike-<topic>/
├── README.md        # 验证问题、假设、步骤、结论、后续建议
├── run.sh 或等价命令 # 可复现的最小验证入口（可选）
└── evidence/        # 日志、截图、耗时与费用数据（可选）
```

## 四、必须写清的四个要素

每份探针 `README.md` 开头必须按顺序给出：

1. **验证问题**：一句话说明要回答什么，例如“DeepSeek 兼容接口在 5 并发下的 P95 延迟与错误率是多少？”
2. **假设**：预期结果与判断依据。
3. **实验步骤**：可被他人复现的命令、配置（密钥脱敏）、样本量。
4. **结论**：明确写 `结论：可行 / 不可行 / 有条件可行`，并给出数据支撑、限制条件与后续建议。

缺少“验证问题”或“结论”的探针视为未完成，不予评审。

## 五、硬性规则

1. **时间盒**：每个探针设定明确时限（建议不超过 1 天），超时即停止并输出阶段性结论。
2. **不写业务代码**：探针代码仅为验证用途，**禁止合入 `src/`**，也不得被业务代码直接 `import`/复制。
3. **可丢弃**：探针结束后，结论沉淀到 `adr/` 或 `plans/`；验证代码可删除或原样保留在探针目录。
4. **可复现**：记录依赖版本、命令、样本与日期；涉及外部 API 时记录费用估算。
5. **脱敏**：禁止提交密钥、Token、真实学生数据；配置用环境变量占位。
6. **结论先行**：文档开头给结论，细节在后；不得只贴代码不给判断。
7. **评审**：探针结论由集成负责人评审；涉及跨模块契约的，按 `plans/module-ownership.md` 的接口变更流程处理。

## 七、已确认事项

- 探针模板：采用本文件第四节的四要素结构，不再单独维护模板文件。
- 探针结论评审：集成负责人评审，必要时请模块组复核。
- 探针代码保留：允许保留在 `docs/spike/spike-<topic>/`，但不得进入 `src/`、`tests/` 或生产构建。

## 八、与正式实现的关系

- 探针是**降低风险的证据**，不是实现草稿。
- 探针结论被采纳时，在 `adr/` 记录决策，再由对应模块组按 `spec/` 重新实现。
- 若探针结论与既有 spec 冲突，先更新 spec/ADR，再改代码。
