# spec/ — 规格说明目录

本目录存放项目的需求与模块规格，是从 `context.md` 与原始资料（`docs/reference/`）提炼出的、可被实现与验收引用的需求事实来源。规格与原始资料冲突时，以最新评审通过的 spec 为准，并在 `adr/` 记录取舍。

## 1. 用途

- 为 Issue、PR、测试用例提供统一的需求依据。
- 明确“做什么、做到什么程度”，不承担架构取舍（架构决策写入 `adr/`）。
- 记录尚未收敛的待确认项，避免被静默假设。

## 2. 文件与命名

| 文件 | 说明 |
| --- | --- |
| `README.md` | 本文件：目录规则 |
| `spec-vX.Y.md` | 全局规格骨架/总览（当前 `spec-v0.1.md`） |
| `<module>-spec-vX.Y.md` | 模块规格，`<module>` ∈ `qbank` / `exam` / `grading` |

约定：

1. 版本号从 `v0.1` 起，按 `主版本.次版本` 递增；结构或范围变化升主版本，澄清与补充升次版本。
2. 每个文件头部必须包含：版本、状态、日期、负责人、关联 Issue。
3. 需求条目编号在规格**评审通过后**由集成负责人统一分配，禁止各人自行编造编号。`v0.1` 为骨架，不分配正式 FR 编号。
4. 一个需求条目只描述一个可验证的能力，避免“以及”“等等”这类不可验收表述。

## 3. 状态与流转

状态取值：

- **草稿**：作者自用，未提交评审。
- **评审中**：已开 PR，等待模块 owner 与集成负责人评审。
- **已冻结**：评审通过，可作为实现与验收依据；修改须按第 4 节走新版本。
- **已废止**：被新版本或 ADR 取代，文件保留并注明替代者。

流转：草稿 → 评审中 → 已冻结；已冻结 → 已废止（或升版后重新评审）。

## 4. 评审与冻结规则

1. spec 变更须走**独立 PR**（见 `agent-rules.md` 第 2 节契约文件规则），PR 中不得混入业务代码。
2. 评审人：至少 1 名相关模块 owner + **集成负责人**；跨模块规格需涉及模块双方 owner 确认。
3. 冻结条件：
   - 背景、目标、范围、Non-Goals 与 `context.md` 一致；
   - 所有待确认项已关闭，或保留但明确负责人与截止日期；
   - 验收标准可测；
   - 评审意见全部处理并留有记录。
4. 冻结后的任何语义修改都必须新建版本文件（不得原地改已冻结版本），并在新文件“变更记录”中说明差异；旧文件状态改为“已废止”或保留历史。
5. 实现中发现 spec 不可行：提交 ADR，经集成负责人批准后修改 spec，不允许代码与规格长期分叉。

## 5. 与其他文档的关系

- `context.md`：项目上下文与锁定决策，spec 不得与之矛盾。
- `agent-rules.md`：协作与所有权规则。
- `adr/`：架构与方案取舍，spec 只引用 ADR 编号，不复述决策过程。
- `plans/`：迭代计划，不得替代 spec 定义需求。
- `docs/reference/`：原始资料，只读归档。
